ContextOS Architecture & Core Decisions

A complete project brief synthesized from your historical AI conversations.

Project Context & Objective

ContextOS functions as a personal, durable memory substrate for knowledge work. Its primary directive is enabling multi-turn conversational AI collaboration across distinct toolsets and platforms without ever resetting the operator's intellectual continuity or project state.

Architecture

The engine operates on a local-first, zero-telemetry client execution model. The entire historical transcript graph, semantic indexing, and document synthesis pipeline run directly within the browser runtime using SQLite-WASM backed by the Origin Private File System (OPFS) for persistent, unmetered storage.

Important Decisions

Local SQLite via WebAssembly instead of IndexedDB

IndexedDB key-value stores introduced unacceptable transaction serialization overhead when running recursive semantic graph walks across 20,000+ conversation nodes.

Clean Editorial Prose over Rigid XML Schemas

Standard structural payloads consumed up to 35% of the context budget on delimiter parsing, inducing hallucinated attribute omissions in complex prompts.

Self-Contained In-Process Embeddings

Removed remote vector database dependencies entirely. Context extraction occurs strictly on raw semantic similarity generated through compact local ONNX models.

Decision Rationale

Direct relational SQLite queries guarantee strict ACID stability during bulk ingestion of multi-megabyte ChatGPT and Claude exports. Furthermore, empirical evaluations revealed that frontier foundation models maintain significantly higher reasoning fidelity and causal recall when supplied with dense, human-curated editorial prose rather than heavily tokenized tabular formats.

Explored & Abandoned Approaches

  • —Supabase Edge Gateway streaming proxy: Abandoned due to persistent request timeouts when aggregating 400KB transcript payloads across unstable mobile networks.
  • —BroadcastChannel multi-tab sync: Resulted in race conditions and duplicate SQLite transaction locks when two active browser sessions wrote simultaneously. Replaced by WebLock concurrency primitives.

Known Constraints

Chromium memory ceiling limits single-worker WASM heaps to approximately 2GB on mobile devices, necessitating streaming chunk synthesis for export files exceeding 120,000 raw prompt turns.

Open Questions

Currently evaluating whether to implement sliding-window conversational rollups automatically after 30 days, or preserve granular verbatim turn trees indefinitely using AST hierarchical compression.
